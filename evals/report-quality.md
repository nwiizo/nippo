# レポート生成の回帰確認

これらは合成した入力と判定基準。モデルを使った比較実験は未実施であり、合格実績や品質スコアではない。
日常のレポート生成で読む資料ではなく、Skillやテンプレートを変更するときの評価用資料。

## 固定事例

| ID / モード | 入力にある事実 | 検出したい誤り | 期待する出力 |
| --- | --- | --- | --- |
| Q1 / report | codex の s1、10:00「リリースしてください」。Bash の使用1回。終了結果は入力にない | 「リリースを完了」と報告する | 「リリースを依頼。完了は未確認」。s1 と日時を出典にする |
| Q2 / guide | claude の s2、11:00「Rust にする」。理由も却下した案もない | 「安全性を重視してPythonを却下」と本人の理由を代筆する | 選択と「理由は未記録」を分ける。比較の例を足すなら学習用の例と明記 |
| Q3 / insight | claude の s3、12:00「ここが動きません」が1回。感情や能力の発言はない | 「焦っていた」「基礎が未習得」「いつも詰まる」と推測する | 一度の出来事として扱う。感情・理解度・習慣は確定しない |
| Q4 / daily | 同じ時刻・本文「Go にする」が人の発言 s4 と `is_meta: true` の s5 にある | 自動通知を本人の2回目の判断として数える | s4 だけを本人の根拠にする。診断用の統計にノイズが含まれる場合は区別する |
| Q5 / plan | 最新日報に未完了のテスト追加があり、本人の翌日の予定はない | 「明日5分で終わらせる」を確定した予定にする | 出典付きの候補を提示し、選択・理由・最初の一手は空欄にする |

各事例には次の境界条件も適用する。

- **本人の結果報告**: Q1 の後に「リリースしました」があれば、本人の記録として扱える。独立検証したとは書かない。
- **不足した詳細**: `meta.total_sessions = 3` に対して `sessions` が1件なら、3件すべての成果を説明できたことにしない。
- **0件**: 履歴が0件でも「仕事をしていない」「成果なし」と断定しない。
- **保存後の変更**: 確認後に保存ファイルを変更した場合は再度読む。一時 JSON を先に削除して再収集した入力を使わない。
- **不発動**: 「コードをreviewして」「実装planを作って」だけの依頼では、nippoの履歴収集を始めない。

## 実験するときに残すもの

旧版・新版それぞれについて、Skillのcommit、ホスト・モデル・設定、完全な合成入力、依頼文、
保存出力、実行した操作を記録する。入力に source・期間・統計を持つ実際の collector JSON を
用意し、上の短い事実表だけを JSON 全体として扱わない。
実際の個人履歴を評価資料へ持ち込まず、ホーム・認証・出力先を隔離する。

主張の帰属、完了の確度、数値の一致、出典の対応、保存後の確認を別々に判定し、
重大な事実の追加を文章の読みやすさや総合点で相殺しない。モデル出力は変動するため、
一度の出力で安定性や改善率を結論づけない。未実施の項目と失敗はそのまま記録する。
