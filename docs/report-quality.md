# 根拠と保存結果の確認

文章を作る前と、保存後に使う。実行した確認と未確認事項を区別し、文章の品質に点数を付けない。

## 書く前に確認する

collect の JSON を使うモードでは、対象期間・timezone・requested/resolved source を確認する。`sessions` の件数が
`meta.total_sessions` より少ない場合は、詳細が省略されている。統計だけの入力や省略された
詳細から、個別の成果や判断を補わない。プロンプトも先頭500文字で切れている場合がある。
不足により目的を満たせなければ、その範囲を伝える。
brief は取得した summary、plan は読んだ日報と任意の ledger、ledger はCLIの結果を照合対象にする。

入力ごとに使える根拠を分ける。

| 書く内容 | 確認するもの | 足りない場合 |
| --- | --- | --- |
| 期間・source・件数・利用量 | `meta` / `stats` / `render_helpers` | 値を作らず未確認とする |
| 本人の依頼・選択・理由 | `user_prompts` と日時・session ID、`decisions` の原文 | 選択はあっても理由がなければ「理由は未記録」。候補の検出を判断の確定とみなさない |
| 実行・完了・効果 | 本人が明示した結果と、その発言の出典 | 依頼やツール使用だけなら「依頼」「完了未確認」。本人の報告は「本人の記録による」と区別する |
| 傾向・改善案 | 具体的な複数の記録、または提案のきっかけになった記録 | 一例を習慣に広げない。代替案・学習例は「提案」「例」と示す |
| plan / ledger の内容 | 読んだ日報のファイル名と該当箇所、ledger の項目 | 新たな履歴確認や本人の選択が済んだことにしない |

成果・判断・傾向には短い出典を添える。例えば `codex / session s1 / 10:00`、
`nippo-2026-10-29.md の Unclear points`。同じ段落で出典を共有できる場合はまとめる。
出典の識別子は入力にある値だけを使い、ローカルの絶対パスや履歴全文を不要に転載しない。
`is_meta: true` の発言は本人の依頼・判断の根拠にしない。

## 保存した本文を照合する

保存したファイルを Read で読み直し、今回の入力と次の5点を照合する。
文章の調整をした場合は、その変更を含む保存済みファイルでもう一度確認する。

1. **範囲と数値**: 日付、timezone、source、プロジェクト、件数が入力と一致する。活動の記録間隔を実労働時間、ツール回数を成果や能力として説明していない。
2. **主張の強さ**: 依頼を実行済みに、予定を完了に、本人の報告を独立検証済みに変えていない。条件・否定・比較対象・未確認事項が落ちていない。
3. **根拠の対応**: 出典が実在し、その記録が本文の主張を支える。理由・感情・他者への効果を作っていない。提案を本人の決定として書いていない。
4. **用途**: report は成果と相談事項を区別する。reflection / plan の本人の記入欄は空白のまま。guide の学習例は実際の判断理由と区別する。
5. **保存結果**: 呼び出し元の `reports/` に意図したファイル名で保存され、途中で切れていない。brief は収集した summary と一致する。ledger はCLIの結果を確認する。

確認できるまで一時データを削除しない。確認のためだけに履歴を再収集すると入力が変わるので、
今回の入力を使う。trend は各区間の本文と集計をその区間の JSON に照合してから一時データを
置き換え、最後に保存した全体の期間・区間の重複・文章を確認する。

## 完了の伝え方

保存先と、確認した範囲を短く伝える。例えば「期間・統計・記載した出典を入力と照合しました」。
全文や必要な入力を確認できなかった場合は未確認の範囲と理由を添える。
この手順はAIによる読み比べであり、機械検査・ハッシュ照合・成果の独立検証を実行したとは書かない。
入力が正しいことや文章の意味がすべて保たれたことを保証するものでもない。
